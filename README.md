# dsh-AIO 工作台插件

适用于 Windows x64 上的 DeepSeek Harness Desktop 0.2.1-rc.2。插件内置 AIO Tauri 2.0.7 绿色版，运行时需要 WebView2。安装后，Harness 侧栏底部提供一个「AIO」按钮。点击后，AIO 在独立窗口中打开或将已运行的工作台切到前台。对话、项目、终端、设置及弹窗都在 AIO 窗口内操作。

## 安装

启动一次 Harness Desktop 以初始化 `desktop` profile。插件包已包含 AIO。在 Harness 的插件管理界面安装 `dsh-aio-workbench-0.3.1.tgz` 或此仓库的 `plugin` 目录并启用，然后重启 Harness Desktop 加载侧栏按钮。也可以退出 Harness 后，从交付仓库根目录使用 Desktop 自带的 `dsh` 命令安装发行包。

```powershell
$bundle = (Resolve-Path .\dsh-aio-workbench-0.3.1.tgz).Path
dsh plugin --profile desktop add "file:$bundle"
```

从源码运行 Desktop 时，通过该实例的插件管理界面安装。生成发行包时，将 `plugin` 目录复制到临时目录，把根目录的 `README.md` 一并复制到该副本，再对副本运行 `npm pack`。这样发行包包含完整说明，仓库只维护根目录这一份 README。

## 使用

展开 Harness 左侧栏，然后点击底部的「AIO」，然后在 AIO 窗口内选择项目、运行时并开始对话。按钮也可在没有打开 Harness 会话时使用。关闭 AIO 后，再次点击「AIO」即可打开它。

插件默认校验并启动随包的 Windows x64 绿色版，来源为 [AIO v2.0.7 Release](https://github.com/AncoderAI/AIO/releases/tag/v2.0.7)。AIO 负责解包和管理其应用数据。自定义安装位置可在启动 Harness 前将环境变量 `AIO_TAURI_EXECUTABLE` 设为 AIO Tauri 可执行文件的绝对路径。按钮出现感叹号时，将鼠标移到按钮上或用键盘聚焦，查看失败原因。

## 升级和卸载

从旧版升级时，先在 Harness 的插件管理界面卸载旧版，再安装并启用新版。卸载插件只移除 Harness 的入口，AIO 的项目和会话由 AIO 管理。

## Harness 已经能带一队 Subagent，为什么还需要 Bot 管一队 Agent？AIO、T3code、Cindy、Orca、Paseo、Herdr这类工具会是过渡产品吗？

Codex 桌面端已经能同时打开多个项目和会话。M 个项目，每个项目 N 个会话，就有 M×N 条可以并行推进的工作线。按我的使用体验，关掉 Codex 再打开，任务还能接着上次的位置继续。现在也有了 Bot 入口，可以把指挥 Agent 的操作延伸到桌面之外。

这也引出一个问题：当原生桌面端已经能管理多个项目和会话，Harness 又能让一个主 Agent 带一队 Subagent，为什么还需要一个 Bot 来管理一队独立 Agent？AIO、T3code 这类工具的价值，会不会只剩下跨供应商切换？

### 一次任务里的分工，和一个项目里的分工

假设我要审查一次支付改造。主 Agent 可以派三个 Subagent 分别核对接口兼容性、异常处理和测试覆盖，再把结果汇总起来。目标由主会话给定，几项调查并行展开，最后回到同一个交付结果。Harness 里的 Subagent Team 很适合这种工作。

如果是从头做支付改造，任务的生命周期就不同了。后端 Agent 要在独立分支上细化方案、实现接口，可能要连续推进几天。前端 Agent 可以先用 mock 开工，再按接口变更调整。测试 Agent 平时等事件，合并后跑回归，失败时再通知对应负责人。每条线都有自己的计划、工作目录、进度和阻塞，也都有可能单独暂停、恢复或交给人接手。

主 Agent 当然可以给 Subagent 写一份很长的任务说明。真正的问题是，第二天团队成员能否直接打开其中一条工作线，看到它改过哪些文件、为什么停下、接下来准备做什么，并补充指令。对部门级流程来说，这些记录还要能回看和审计。独立会话给每条工作线一个明确的入口。执行层保存任务状态后，这条线还可以按自己的节奏运行，跨天等待，或者持续接收新任务。

至于执行者，有的环节用通用 Agent 加垂直 Skill 就够了，有的环节可以交给专门的 Agent，比如一个只负责生成、运行和分析单元测试的 Agent。只要它们有可查看的状态和明确的输入输出，就能作为同一条流程里的独立环节。

### Bot 把指挥入口带到手机和团队群

设想我在手机上的飞书群里发一句：“后端继续做支付接口，前端先用 mock，接口合并后跑回归。”Bot 可以把任务分给办公室电脑、另一台 PC 或云端的执行器。后端 Agent 遇到阻塞就在群里更新，前端 Agent 可以继续做自己的部分，测试 Agent 等合并事件再启动。团队成员可以在群里追问，也可以打开对应会话看代码或接手。

协调工作仍然可以由一个 Agent 来做。这个协调 Agent 通过 Bot 收指令、处理依赖、汇总进度，通过调度服务把任务交给独立执行器。只要任务和进度有持久化记录，协调 Agent 重启后就能重新读到状态。一台执行机器掉线时，其他机器上的工作可以继续，受影响的任务则可以恢复或重新派发。

这也是 7×24 小时流程需要考虑的事。有人审批时才推进的 Agent、收到代码变更就启动的测试 Agent、持续处理队列的 Agent，各有各的运行节奏。它们能否跨机器运行、能否独立恢复，取决于 Bot 背后的调度和执行系统。飞书群提供的是团队随时能用的入口。

### 当你想同时跑 100 个 Agent，派活也要考虑成本和容量

假设一台 PC 受内存限制，只能稳定跑 10 到 20 个 Agent。要同时跑 100 个，就得把负载分到多台 PC 或云端。账号也有自己的并发和用量限制，有的套餐跑几个小时就会碰到五小时用量上限。如果某个 Harness 实例只绑定了一套凭证，额度耗尽时，调度器就得把新任务发到仍有容量的执行器。100 路并行能提高吞吐，实际提效多少还要看任务之间有多少依赖，以及评审、合并能不能跟上。

模型也可以按任务选。复杂需求、架构设计和高风险决策，值得用能力更强的模型。中等复杂度的实现、批量迁移和回归测试，可以用成本更低的模型或专用 Agent。不同 Coding CLI 也各有长处。即使某个 Harness 支持给 Subagent 选不同模型，跨账号分配额度、跨机器安排执行，以及跟踪每条工作线的状态，仍然需要相应的调度能力。

当每月用量到了 100 亿 Token 以上，各家 Coding Plan 的折扣、模型升级和用量窗口都会直接影响成本和排期。这个月划算的组合，下个月可能就变了。能把任务发到合适的模型、账号、CLI 和机器上，本身就有价值。

### AIO、T3code、Cindy、Orca、Paseo、Herdr这类工具会是过渡产品吗？

如果AIO（[https://github.com/AncoderAI/AIO.git](https://github.com/AncoderAI/AIO.git)）、T3code、Cindy、Orca、Paseo、Herdr这类工具主要解决的是切换 Key，而我只用一家模型供应商，Codex 加上顺畅的编辑器联动，可能已经够了。原生桌面端越完整，单纯汇集多个供应商入口的价值就越小。

如果这类工具能管理独立工作线，处理跨设备派活、按额度分配任务、跟踪进度、恢复中断，并让团队随时查看和接手，那么即使用同一家模型，它也解决了团队协作的问题。

我会把两层叠起来用。**Bot 管项目里的多条工作线，每条工作线上的主 Agent 再用 Harness 的 Subagent Team 做局部并行。** Bot 把支付改造交给独立的后端 Agent，后端 Agent 再派 Subagent 查接口、读历史代码、核对测试。

我判断要不要加 Bot，就看一个场景：**发起任务的会话关掉以后，明天我还能不能在手机上看到每条工作线的进度，接手其中一条，同时让其他工作继续跑？**
